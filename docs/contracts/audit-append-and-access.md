# Audyt dopisywany — kontrakt #16

Źródła: [PRD MVP 3.1](../product/PRD.md), [wymagania C-F151, C-N019, C-N037, C-N039–040, FR-ADM-070–071](../WYMAGANIA_AUTERVA.md), [architektura](../ARCHITEKTURA_AUTERVA.md) i [D-10](environments-hosts-operations.md). Pełny ekran przeglądu nie należy do #16.

`appendAudit(tx, input)` działa **wewnątrz tej samej transakcji PostgreSQL**, która zapisuje krytyczną zmianę. Przyjmuje identyfikator rzeczywistej sesji, aktora i docelowej firmy; na aktualnych wierszach ponownie sprawdza MFA, rolę, stan konta/firmy i izolację A/B. Roli nie przyjmuje z payloadu. Superadmin pozostaje `SUPERADMIN_AUTERVA` także przy zmianie firmy A/B; nie jest adminem tej firmy. Akcje zarządzania firmą, zaproszeniem, okresem, domeną, brandingiem i ustawieniami wymagają superadmina. Operacje floty/mediów/blokad dopuszczają także admina własnej firmy, lecz ich przyszły use case musi niezależnie zweryfikować host, zasób, dane wejścia i reguły domenowe. Audyt nie jest zamiennikiem autoryzacji mutacji.

Każdy wpis zapisuje UTC `createdAt`, aktora i rolę, firmę docelową, typ i ID obiektu, działanie, serwerowy `requestId` i `eventKey`. Jedno żądanie z kilkoma wpisami używa jednego `requestId`; osobny `eventKey` identyfikuje logiczne zdarzenie przy retry. Unikalność `eventKey` odrzuca duplikat i cofa całą ponowioną transakcję, także zapis domenowy. Wywołujący może odczytać wcześniejszy wynik operacji wyłącznie przez własną kontrolowaną ścieżkę idempotencji; nie wolno uznać błędu duplikatu za sukces nowego zapisu. Starsze wiersze mają `eventKey=NULL` po addytywnej migracji; pozostają czytelne.

`changes.changedFields` dopuszcza jedynie nazwy pól z allowlisty, bez wartości tekstu firmy, kontaktu, opisu, notatki, czatu, hasła, tokenu, kodu MFA ani IP. `before`/`after` dopuszcza tylko wąskie bezpieczne pola stanu, dat i liczników, krótkie wartości enum/ISO/boolean/liczby. Niedozwolony klucz lub wartość odrzuca cały wpis. Operator odzyskujący MFA występuje jako osobny `operator:<id>`; w audycie jest skrót referencji dowodu, potwierdzenie weryfikacji i liczba cofniętych sesji, nigdy referencja surowa. Login jest sukcesem audytowym dopiero po potwierdzonym TOTP i utrwaleniu pełnej sesji. Ograniczona sesja po haśle nie jest logowaniem do panelu; wylogowanie pełnej sesji zapisuje audyt atomowo z jej unieważnieniem. Odzyskanie/rotacja MFA również zapisuje bezpieczne zdarzenia we własnej transakcji.

`listAudit` jest wewnętrznym, ograniczonym do 100 wierszy odczytem po sesji i firmie. Admin A nie może odczytać B, a superadmin jawnie wybiera firmę. Nie ma zwykłego API do edycji, usuwania ani publicznego przeglądu audytu. Dopuszczalne operacje aplikacyjne tylko dopisują; właściciel bazy i migrator mają techniczną możliwość zmiany danych, więc nie deklarujemy niezmienności wobec tych uprawnień.

Typowane akcje obejmują auth (ukończony login, logout, hasło/sesje/MFA), firmę, zaproszenie, okres, domenę, branding, ustawienia, pojazd (utworzenie/zmiana/publikacja/ukrycie/archiwizacja), media i CRUD blokady. W #16 działający konsumenci to auth i odzyskiwanie operatora; nie istnieją jeszcze mutacje firmy/floty/mediów, dlatego ich wpisy będą wdrażane razem z właściwymi use cases, bez fikcyjnych zdarzeń. Każdy przyszły zapis krytyczny musi użyć `appendAudit` w swojej transakcji i testu rollback/A-B/rzeczywistej roli.

Retencja audytu wynosi 365 dni według D-10. Ten moduł nie usuwa wierszy i nie realizuje eksportu ani docelowego storage; kontrolowana ścieżka maintenance/retencji należy do [#108](https://github.com/KarolR2001/Auterva/issues/108), po wdrożeniu workera #17, z logiem wykonania i bez endpointu panelu. Archiwizacja firmy nie czyści audytu. Przed wydaniem trzeba potwierdzić rzeczywisty storage, politykę retencji i test usuwania/eksportu po terminie.
